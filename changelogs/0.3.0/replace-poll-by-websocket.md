# Replace polling by server-sent events

## Currently

- The dependency graph of a submission is loaded over REST with `useSubmissionGraph` ([use-submission-graph.ts](../../apps/web/src/modules/submission-dependency/hooks/use-submission-graph.ts)): React Query, key `submissionDependencyKeys.graph(id)`, calling `GET /submissions/:id/graph`. The graph it gets back is also written into the cache of every other node, because they share the same connected component.
- [dependency-graph-provider.tsx](../../apps/web/src/modules/submission-dependency/components/dependency-graph-provider.tsx) (mounted by [submission-form.tsx](../../apps/web/src/modules/submission/components/submission-form.tsx)) counts how many hooks are asking for updates (`pollers`). While that count is above zero, it passes `refetchInterval = DEPENDENCY_POLL_MS` (2000 ms, [submission-dependency.constants.ts](../../apps/web/src/modules/submission-dependency/submission-dependency.constants.ts)), so the whole graph is fetched again every 2 s.
- The only hook that asks is the refer submission widget ([refer-submission-widget-item.tsx](../../apps/web/src/modules/template-widget/components/items/refer-submission-widget-item.tsx)), through `useDependencyPolling(isApplying)` ([use-dependency-polling.ts](../../apps/web/src/modules/submission-dependency/hooks/use-dependency-polling.ts)). Clicking **Apply** writes an ISO timestamp into the widget value in the Yjs doc.
- The web app cannot tell when the apply has finished. The change goes Yjs doc → Hocuspocus `onStoreDocument` (debounce `DOCUMENT_STORE_DEBOUNCE_MS` 1 s, max 5 s, [collab.gateway.ts](../../apps/collab/src/modules/collab/collab.gateway.ts)) → `SubmissionService.sync` → `PUT /submissions/:id/values` → `SubmissionBehaviorsService.applyBehaviors` ([submission-behaviors.service.ts](../../apps/api/src/modules/submissions/submission-behaviors.service.ts)), which creates or deletes the referred submissions and their dependencies. Nothing reports back to the browser when this is done.
- Because of that, `useIsReferApplying` ([use-is-refer-applying.ts](../../apps/web/src/modules/template-widget/hooks/use-is-refer-applying.ts)) guesses: "applying" means `appliedAt + REFER_SUBMISSION_APPLY_TIMEOUT_MS` (30 s) has not passed yet and the steps still show changes. For up to 30 s the graph is fetched every 2 s (about 15 requests, each running the recursive CTE over the whole component), even when the apply finished after the first one. If the apply fails or takes longer than 30 s, the spinner simply stops and nothing explains why.
- Outside an apply nothing refreshes the graph: dependencies changed by another user or another tab appear only after a reload, a remount, or once the global `staleTime` (60 s) expires.
- A websocket already exists: Hocuspocus in `apps/collab` (`COLLAB_WS_PORT`), which the web app opens per document (`submission/<id>`, template docs) to sync Yjs. It carries only document state. The api has no websocket and no way to push an event to the web app or to collab.

## Acceptance Criteria

- [x] Setup socket-io for `web` and `api` → replaced by NestJS `@Sse` (no socket.io)
- [x] Remove poll method
- [x] When update from context -> emit with event
- [x] Event listener emit socket for 2 type full-values and simple value (only title, updated, ...)
- [x] Change `submission-graph` using socket to update graph when node or dependency changes

## Solutions

- [x] Shared contract in `@tomato/constants` (`RealtimeEvent`: `submission.values` / `submission.summary` / `submission.graph-changed`, `RealtimeRoom`: `board` / `submission`, separators) and `toRealtimeRoom(kind, id)` in `@tomato/utils`
- [x] Api module `realtime`: `GET /rest/realtime?rooms=board:<id>,submission:<id>` (`RealtimeController`, `@Sse`), rooms validated by `RealtimeQueryDto` (pattern `<kind>:<uuid>`, otherwise `400`). `RealtimeService` is an rxjs `Subject`: `emit(room, event, payload)`, `stream(rooms)` filters by room and merges a `ping` every `REALTIME_HEARTBEAT_MS` (15 s) so the Next.js rewrite (30 s proxy timeout) keeps idle streams open. No new env: the web reaches it through the existing `/rest/core` rewrite
- [x] New package `@tomato/events` (for every Nest app): global `EventsModule` (wraps `EventEmitterModule.forRoot()`), `EventBusService.emit(event)` keyed by the event's class name, `@OnDomainEvent(EventClass)` (an `@OnEvent` on that name), base class `DomainEvent`; no event-name constants. Class names must be unique within an app. Imported by the api `AppModule`
- [x] Events: `SubmissionsService.updateFromContext` emits `SubmissionUpdatedEvent` with the stored row (`updateValues` now returns `id, boardId, data, dataDisplays, title, updatedAt`); `remove` emits `SubmissionRemovedEvent`. `SubmissionDependenciesService` emits `SubmissionDependenciesChangedEvent` (`sourceId`) itself when `deleteReferencedExcept` / `createReferDependencies` (repository now returns counts) actually deleted or created something, so `SubmissionBehaviorsService` and `ApplyChangesContext` are unchanged
- [x] `SubmissionsRealtimeListener` (submissions module): full values → `board:<boardId>` (`submission.values`), simple `{ id, title, updatedAt }` → `submission:<id>` (`submission.summary`), `submission.graph-changed` → `submission:<id>` when it is deleted. `SubmissionDependenciesRealtimeListener` (submission-dependencies module): `submission.graph-changed` `{ id: sourceId }` → `submission:<sourceId>`. A refer apply that both deletes and creates sends two `graph-changed`; the web dedupes in-flight refetches
- [x] Web `shared/lib/realtime`: one `EventSource` for the union of the joined rooms (ref-counted, batched per tick); when the set changes a new stream is opened and the old one closed once the new one is `open`, so no event is lost while switching (events may arrive twice in between; every handler is idempotent). `useRealtimeRooms(rooms)` / `useRealtimeEvent(event, listener)`
- [x] `useSubmissionGraph(id)`: no `refetchInterval`; joins the room of every node, patches the node title in every node's cached graph on `summary`, invalidates every node's graph on `graph-changed` (`cancelRefetch: false`, so the provider and the sidebar reading the same graph refetch once). `useDependencyPolling`, `requestPolling`, `DEPENDENCY_POLL_MS` removed; the refer widget keeps `useIsReferApplying` (30 s) only as the spinner's upper bound
- [x] `useBoardSubmissions` joins `board:<boardId>` and merges `submission.values` into the cached row
- [x] Risks / not covered: no auth on the stream (same as the rest of the api); rooms travel in the URL, so a very large component makes a long query string; submissions created on another board by a refer behavior are not pushed to that board's table (only updates are); a stream reconnecting after a drop (`EventSource` retries by itself) misses the events sent while it was down
